# 实施约束

## 开始实现

1. 读取 Issue 和固定验收目录，将相关 E2E 用例保存为 `docs/e2e/issue-<编号>.md`。每个用例使用五列：**用例编号、验证目的、验证步骤、预期结果、所属 Issue 编号**。沿用稳定子例 ID，每个必选输入单独列出；步骤足以复现，预期必须能判定成功或失败。
2. 在开始实现前，用 `gh issue comment --body-file` 将该文件完整发布为对应 Issue 评论，再回读核对正文；本地记录评论链接。用例变化时同步更新本地文件并发布新修订，回读后继续实现。计划与实际执行结果分别保存。
3. 复用 `Makefile` 执行重复命令；新增生成、构建、检查或验收入口时同步补充 target 和 `make help` 说明。运行目标集群的命令必须显式传入环境参数。

## 代码与提交

- 提交标题采用 `type: 中文说明`，例如 `feat:`、`fix:`、`chore:`、`docs:`、`test:`、`refactor:`；合并提交也带前缀。标题说明具体行为。
- 在模块、函数或职责切换处添加简洁中文注释，说明基本功能和作用。关键安全/一致性/恢复边界使用 `关键：` 特殊标注，解释约束为何存在及破坏后的后果；例如授权、事务原子性、UID/RV 条件写、可能已发送、凭据清除、恢复禁重放。
- 注释描述当前行为与原因，随实现同步修改；生成文件由生成器维护，功能说明写在手写 IDL 或封装层。

## 完成检查

确认 E2E 五列完整、Issue 评论与本地版本一致、必选子例都有独立实际结果；确认相关 Makefile 入口和关键注释齐全后提交。成功、失败、未执行、环境失败分别报告，保留真实 testedCommit，不把计划当成通过记录。

本约束自 2026-10-18 本轮补充起应用。已经发布并被运行证据引用的提交保留原 SHA；新增及尚未发布的提交按新标题格式执行。
